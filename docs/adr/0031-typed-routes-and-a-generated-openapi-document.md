# ADR 0031 — Routes return typed records; the hosts generate the OpenAPI document

- **Status:** Accepted 2026-11-10 — built in the same PR.
- **Date:** 2026-11-10.
- **Relates to:** **Amends [ADR 0028](0028-backend-moves-to-dotnet-and-postgres.md)**,
  only its "the HTTP contract does not change" clause as the port read it:
  byte for byte with Flask. Field names, absent-versus-null and status codes
  stand, because the app and `packages/insolvia_api_client` read them.
  [ADR 0030](0030-three-backend-layers.md) gains one library, `Insolvia.Http`.
  [ADR 0029](0029-one-testing-shape.md) is unchanged: `contract/` still owns
  the wire shape.

## Decision

**Every route handler returns a typed record or a typed result**
(`DebtorView`, `Created<CaseView>`, `Results<Ok<X>, JsonHttpResult<ErrorBody>>`,
`NoContent`), never a hand-built `JsonObject`. One `System.Text.Json`
configuration (`WireJson`) writes them all: camelCase by default,
`[SnakeCase]` where the wire is snake_case, a domain record's unanswered
members left out, `[Flatten]` to inline a nested record's members.

**The OpenAPI document is generated by each HTTP host from those types**
(`Microsoft.AspNetCore.OpenApi`, `WireOpenApi`), with the handlers' doc
comments as summaries. The hosts serve it at `/openapi/v1.json` and as a
reference page at `/docs`. `docs/reference/openapi/{api,admin}.json` are
committed copies: `OpenApiDocumentTests` fails when a copy is stale, and
`backend/scripts/dev-openapi.sh` rewrites both. The TypeScript route tables
that used to generate them (`tool/openapi/`, `npm run openapi`) are deleted.

**The Flask byte quirks are dropped.** Python is gone (plan 18.23), and
nothing reads the quirks:

- sorted keys, ASCII-escaped text, and bare `application/json` (now
  `application/json; charset=utf-8`, keys in record order);
- a 204 that said `text/html`;
- Werkzeug's HTML 404 and 405 pages. Every error is now the JSON
  `ErrorBody` (`error`, and `message`/`fields` when there are any), including
  an unknown route and a wrong method.

**What the hosts share goes in `Insolvia.Http`**: `WireJson`, `WireFormat`,
`ErrorBody`, `ErrorResponses`, `MethodFallback` and `WireOpenApi`. It is the
one library that references ASP.NET Core, and only the HTTP hosts (`Api`,
`Admin`) reference it. The migrator's image is the plain .NET runtime, so
ASP.NET must stay out of `Insolvia.Platform`.

## Why

- A handler that builds a `JsonObject` says nothing about what it returns.
  The response type was only in the clients' TypeScript, so the document
  had to be generated from the TypeScript, a second statement of the wire
  that could disagree with the server.
- A typed result lets the server describe itself. The document can't drift
  from the code, and a new route is documented by being written.
- Byte parity had a purpose during the port: proving the C# answered
  exactly as the Python did. That proof is done and the oracle is deleted.
  Keeping its quirks would preserve accidents of Flask, not anything a
  client depends on.

## Consequences

- A route change edits its handler's result type and doc comment, then runs
  `backend/scripts/dev-openapi.sh`. There is no table to keep in step.
- `OpenApiDocumentTests` (Api, Admin) fail on:
  - a stale copy;
  - a mapped route the document lacks;
  - an operation with no typed success response.
- The contract suite checks every exchange against the documents, so a
  declared result that disagrees with what a route sends fails there. Its
  validator understands OpenAPI 3.1 type lists and `oneOf`.
- Request bodies are declared with `.RequestBody<T>()`, a docs-only record.
  Routing never sees it. `.Accepts<T>()` would add a content-type constraint
  that turns a route's own 400 into a 415. The parsers still own validation.
- Still free-form, each marked where it is declared:
  - an answer's value;
  - an extraction candidate's payload;
  - a job's result;
  - a case collection's body, documented as `additionalProperties`.
- `packages/insolvia_api_client` stays hand-written. It is no longer what
  the document is generated from, so a generated client becomes possible
  later; that is not decided here.
