Switching Cost & Import

A firm that switches to Insolvia has years of cases in whatever it used before. This spike establishes, from the incumbents’ own public documentation, what actually comes with them — and recommends what to build, and when.

Scope consumer-bankruptcy prep software, desktop & cloud Compiled 2026-09-23 Status spike — a decision and a sequencing call, no code

Why this is a switching-cost question, not a feature

Every path below writes the same place: an extraction_candidate row, reviewed and confirmed by a human before it becomes a case record — the same seam the case data model gives AI extraction and the MCP surface. Nothing about import needs a new invariant. What differs by path is how much of a firm’s history is reachable at all, and that turns out to be the real constraint: the incumbents do not publish enough to make “write a file importer” the whole answer.

Best Case (Stretto) is reported to prepare the large majority of cases filed nationwide; NextChapter is the leading cloud-native alternative. The one pattern every source agrees on

No incumbent — desktop or cloud — publishes a schema for a whole case: debtor identity, assets, exemptions, the SOFA. What is documented is thin and peripheral (a creditor name-and-address list, a claims spreadsheet) or non-existent. The industry’s own switching advice is to re-enter, not migrate. That is the finding this spike exists to record: the bottleneck is not our importer code, it is the absence of anything public to import.

What the courts offer directly

A firm’s own filed cases are independently reachable through PACER / CM-ECF, the federal judiciary’s public access system, regardless of which prep software produced them.

What’s retrievableCostFormSource
Docket reports, the creditor matrix, the claims register, and every filed PDF (petition, schedules, SOFA) — per case, per document, via the firm’s own PACER login. $0.10/page, capped at $3.00 per document (~30 pages); waived under $30/quarter PDF (imaged/text), plus HTML docket pages pacer.uscourts.gov — FAQ

This is a per-document retrieval interface, not a bulk-export API — there is no PACER call that hands back “every case this firm filed” as structured data. But the PDFs it returns are exactly the input shape services/api/src/insolvia_api/core/extraction.py already consumes: that worker turns an uploaded document into candidate records today for credit reports and pay stubs, via one Anthropic call per document constrained to a per-kind structured-output schema, re-validated through the same insolvia_core parse functions every write path uses. A filed schedule is a document like any other to that pipeline; it just doesn’t have a parse_<kind>_output schema yet.

Three candidate paths

All three write extraction_candidate rows — never confirmed case data — so the confirm-before-entry invariant (case-data-model.md) holds identically for all three; none needs a new provenance source or a store change. What differs is what each can actually reach, given the finding above.

PATH 1FILE IMPORTER

Per-format file importers

Parse each vendor’s documented export directly into candidates — today that means NextChapter’s two CSV templates (creditors, claims), written with provenance.source = imported (already in MACHINE_SOURCES, so confirmation is enforced the same as extraction).

Fidelity: high for the ~2 of 25 entity types a vendor actually documents; zero for everything else, because there is nothing public to build against — Best Case publishes no export at all, and reverse-engineering a closed backup format is a different, open-ended undertaking this spike does not recommend.

Effort S per documented formatCoverage narrow
PATH 2RE-EXTRACTION

Re-extract the firm’s own filed PDFs

Treat filed petitions/schedules — supplied by the firm or pulled from PACER — as documents through the existing extraction worker, adding one parse_<form>_output schema+prompt pair per official form, the same shape credit-report and pay-stub extraction already use.

Fidelity: high for whatever was filed — it is the signed, court-accepted record — but it is a snapshot of final values only: no who-typed-what provenance, nothing for cases still open, and none of the dated pay-period history the means test needs (106I is a monthly estimate on the form; the model stores the dated history separately, per case-data-model.md — a filed 106I can’t reconstruct it).

Effort M — one schema/prompt per form (~10–15 relevant forms), pipeline existsCoverage filed cases only
PATH 3MCP HARNESS

Harness-driven migration through the MCP

Per ADR 0013, the firm’s own AI harness — already connected to their old system, however it connects — reads records there and calls propose_case_records on our MCP server like any other candidate write; external_refs names the source system, the origin-pointer seam the data model already carries.

Fidelity: bounded by the harness’s own connector and by how reliably it maps arbitrary content onto our 23 entity shapes — potentially the widest reach (anything the harness can read, proprietary formats included) but the least predictable, and wholly unmeasured until the harness-capability spikes (12.4/12.5) land.

Effort S for us — the tool already accepts this shapeCoverage unbounded, unproven

Recommendation

Build nothing now; sequence a real importer after the client portal (the issue-numbered 15.x work — GitHub milestone “Product · Client portal,” milestone 13) lands, not before it.

Why after, not before

The plan already orders it this way. plan.md places this spike in the “Filing and after” milestone (17.1–17.4) and says plainly that nothing there is scheduled until 13.x lands — which it now has (2026-09-23). This finding does not reopen that ordering; it fills in the reasoning for the step after the spike.

A case needs a client to import into. Practice management (14.1–14.8, not yet built) is what gives a case a client distinct from itself. Importing cases ahead of that milestone means importing into a data model that has nowhere for “whose client is this” to live, and redoing the mapping once 14.x ships.

The design-partner test should run on organic cases first. Two open risks in plan.md — harness capability/adoption (12.4/12.5) and testing web-first “explicitly with the design-partner firm, early” (risk 3) — are both about whether the product works for a case a firm builds in Insolvia. Spending effort on migrating legacy cases before either is validated risks building the wrong importer for a harness or a workflow that hasn’t been proven yet.

The client portal lands the review-queue volume path first. 15.1–15.4 puts debtor-submitted candidates through the same confirm-before-entry review flow an importer of any of the three paths would need at scale. Building an importer before it means building (or scaling) that review UX twice.

Path 1’s ceiling is too low to justify going first. Even the best-documented vendor format reaches two entity types out of twenty-five. The paths that reach further — 2 and 3 — either lean on machinery practice management/portal will also need, or cost us nothing until a harness is proven (12.4/12.5). There is no version of “build the importer early” that outruns those dependencies.

One exception worth naming, not scheduling: if a design-partner firm arrives on NextChapter before 15.x ships, piloting path 1 for its two documented CSVs (creditors, claims) is small enough (S) to do opportunistically without moving the milestone — it is additive to nothing else and touches no shared machinery.
