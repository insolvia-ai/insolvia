# Consuming the design system

**Nothing in this repository publishes the design system.** `@insolvia-ai/design-system`
and `@insolvia-ai/tokens` are built and released in
**[`insolvia-ai/design-system`](https://github.com/insolvia-ai/design-system)**
and arrive here as ordinary published dependencies, like `react` or `expo`.

| Package | Published as | Consumed by |
|---|---|---|
| `@insolvia-ai/design-system` | GitHub Packages, `0.6.x` | `apps/insolvia_app`, `apps/insolvia_marketing` |
| `@insolvia-ai/tokens` | GitHub Packages, `0.2.x` | `apps/insolvia_app`, `tool/reconcile-cognito-branding.ts` |

**One rule: every consumer installs a published, versioned artifact — never
the source by path.** Not a `file:` dependency, not a `link:`, not a workspace
member entry, not "just while I debug this". Both surfaces used to disagree
about this — the app read the package's source through a workspace symlink
while marketing installed a published version — and
[ADR 0010](../adr/0010-design-system-moves-to-its-own-repository.md) is the
decision that ended it. Reintroducing a path dependency for either consumer
recreates a package with two simultaneous truths.

To take a new version, see the `insolvia-design-system-bump` skill. To change
the packages themselves, work in the other repo; its own README covers its
release process.

> Orphaned git tags `insolvia_design_system-v0.1.*` remain on this remote from a
> predecessor package; nothing resolves them, and deleting a published tag is
> irreversible, so they stay.

## The packages publish source — and what that costs a consumer

Each design-system component is three files: `<name>.props.ts` (the shared
contract and variant data — imports no renderer, ESLint-enforced in its own
repo), `<name>.web.tsx` (plain React DOM + Tailwind) and `<name>.native.tsx`
(React Native primitives over `@insolvia-ai/tokens`). The per-component index
re-exports the extensionless `./<name>` and the **consumer's bundler picks the
leaf**.

That resolution step is why the packages have **no build step and publish
`src/` as-is**. Leaf selection belongs to the consumer's bundler, so the
`.web`/`.native` pairs must survive into the published artifact verbatim.

The consequence lands here: **every consumer must transpile TypeScript out of
`node_modules`.** Three of ours do it three different ways, and each needed
saying once:

| Consumer | Mechanism |
|---|---|
| The app's Metro | native; plus a `resolveRequest` override so it picks `.native` on **web** too (`apps/insolvia_app/metro.config.js`) |
| The app's Jest | `transformIgnorePatterns`, derived from `jest-expo`'s in `apps/insolvia_app/jest.config.js` — Jest skips `node_modules` by default |
| Marketing's Vite | `ssr.noExternal` (below) plus `.web` suffixes in `resolve.extensions` |

The Jest one is the newest and the least obvious: it was a non-issue while the
package was a workspace member, because its source sat *outside* `node_modules`.

`theme.css` is generated in the other repo from its `tokens.json` and ships
inside the published package as `@insolvia-ai/design-system/theme.css`.

## What is still generated here

`infra/modules/auth/managed-login-settings.json` — the colours of Cognito's
hosted sign-in page — is generated by
[`tool/reconcile-cognito-branding.ts`](../../tool/reconcile-cognito-branding.ts)
from the **installed** `@insolvia-ai/tokens`:

```bash
npm run tokens
```

`npm run tokens:check` gates it as the required check `Cognito branding`. It
fails on a hand-edit, and also on a tokens bump that did not regenerate — so a
version bump that skips it will not merge.

The tool reads `@insolvia-ai/tokens/colors.json` rather than the package's
`tokens.ts`, because Node refuses to strip TypeScript types under
`node_modules`. Metro and Vite have no such limit, which is why this is the
only consumer that needs the JSON.

## The registry: GitHub Packages

Both packages live on **GitHub Packages** (`https://npm.pkg.github.com`), not
npmjs.org.

**The scope is a contract with the registry.** GitHub Packages only accepts an
npm scope equal to the owning org's login — `insolvia-ai`, not `insolvia` —
and rejects any other scope with a misleading E403
(`Permission permission_denied: The requested installation does not exist.`)
that names neither the scope nor the rule. Keep it `@insolvia-ai` everywhere:
`package.json`, `.npmrc`, imports, docs.

### Authenticating to install

GitHub Packages requires authentication for **every** npm read, including
public packages. There is no anonymous install.

Two `.npmrc` files in this repo carry the scope mapping — one at the root (for
the workspace) and one in `apps/insolvia_marketing/` (deliberately outside the
workspace, with its own lockfile). Both are committed and both contain a
*variable reference*, never a token:

```ini
@insolvia-ai:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
```

npm expands `${NODE_AUTH_TOKEN}` when it reads the file, so a committed
`.npmrc` is safe in a public repo. **Never write a literal token into one.**
Only the `@insolvia-ai` scope is redirected — `react`, `expo`, `tailwindcss`
and everything else still resolve from the public npm registry.

#### Locally

```bash
eval "$(./scripts/github-packages-auth.sh --export)"
```

That script obtains a `read:packages`-scoped token (from `GITHUB_PACKAGES_TOKEN`
if you supply one, otherwise by refreshing your `gh` login's scopes) and exports
it as `NODE_AUTH_TOKEN`. It is idempotent.

#### In CI

Every job that runs the root `npm ci` needs `permissions: { packages: read }`
and the token in the environment:

```yaml
- uses: actions/setup-node@v5
  with:
    node-version: "24"
    cache: npm
- run: npm ci
  env:
    NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

This is newer than it looks: before the extraction, the root install linked the
two packages from source and never contacted a registry at all, so only the
marketing jobs needed it. Now `app-pr`, `app-staging`, `app-prod`,
`api-client-pr` and `branding-pr` all do.

**The packages are in a different repository from these consumers**, so the
automatic `secrets.GITHUB_TOKEN` only works because the packages grant this
repo access (package → *Package settings* → *Manage Actions access*) or are
public. A consumer in a different *org* would need a PAT with `read:packages`;
no such consumer exists.

## Using it

```css
/* Tailwind v4 CSS entrypoint — apps/insolvia_marketing/app/styles/app.css */
@import 'tailwindcss';
@import '@insolvia-ai/design-system/theme.css';
@source '../../node_modules/@insolvia-ai/design-system/src/**/*.{ts,tsx}';
```

The `@source` line is not optional. Tailwind v4 scans your own source for class
names, but the design system's classes live in its published `src` inside
`node_modules`, which Tailwind does not scan by default. Omit it and the
components render completely unstyled — the utilities they reference are simply
never generated. This is the classic "why are my styles gone" bug.

```tsx
import { Button, Card, Field } from '@insolvia-ai/design-system';
```

`react` and `react-dom` are peer dependencies (18 or 19). **`react-native` and
`@insolvia-ai/tokens` are not declared by the package at all** — not as
dependencies and not as peers, optional or otherwise. GitHub Packages strips
`peerDependenciesMeta` from registry metadata, so npm would promote an
"optional" peer to a required one and force every web consumer to install a
native renderer it never loads. The `.native` leaves resolve those imports from
the *consumer's* own dependencies, which is why `apps/insolvia_app` declares
both itself and marketing declares neither.

## The `ssr.noExternal` trick — and why it is mandatory

The marketing site is server-rendered and deployed as a **Lambda container
image**. By default Vite treats dependencies as **external** for the SSR
build — it leaves the bare `@insolvia-ai/design-system` import in the server
bundle and resolves it from `node_modules` at runtime. Marking the package
`noExternal` tells Vite to **bundle its source into the server build
instead**:

```ts
// vite.config.ts (apps/insolvia_marketing/)
ssr: {
  noExternal: ['@insolvia-ai/design-system'],
}
```

Two reasons:

- **It is load-bearing, not just hygiene.** The package publishes TypeScript
  source, and Node cannot import `.ts`/`.tsx` from `node_modules` at runtime —
  so the SSR build *must* transpile and bundle the package. Removing
  `noExternal` does not merely re-introduce a token problem; it breaks the
  server outright.
- **The token stays out of the runtime image.** With the package bundled at
  build time, the private-registry dependency is a build-time-only concern: the
  token lives in the build environment (GitHub Actions), never in the deployed
  image. A registry credential inside a running Lambda image is exactly the kind
  of secret you do not want to have.

**CSS needs no equivalent trick.** `theme.css` *is* shipped in the published
package, but it is never imported by JavaScript at runtime: the site's Tailwind
entrypoint `@import`s it, Tailwind resolves that from `node_modules` while
compiling, and the output is a plain CSS file in the client bundle.
Build-time-only for the same reason as the JS, by a different mechanism, and
nothing needs configuring.

Two things to watch:

- `react` and `react-dom` stay external in the SSR bundle — they are ordinary
  public-registry deps of the site, which is fine. The `.native` leaves and
  `react-native` never enter the web build at all: the resolver never picks a
  `.native.tsx`, and nothing else may import React Native.
- If the site ever adds a second `@insolvia-ai/*` package, add it to the same
  `noExternal` array. A regex (`/^@insolvia-ai\//`) is accepted and saves the
  bookkeeping.

## Iterating on a component and this repo together

There is no local link loop, deliberately. Work on the component in
`insolvia-ai/design-system`, where its Vitest suite and both typecheck programs
run in seconds; publish (a prerelease is fine); then bump the range here.

This is genuinely slower than the workspace symlink the app used to have, and
that is the accepted cost in ADR 0010 — the previous loop was fast because it
skipped the boundary that makes the package a package.
